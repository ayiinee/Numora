# Uji kapasitas Numora untuk 1.000 siswa aktif

**PROPOSED — kriteria QA untuk pengujian kapasitas.** Target 1.000 siswa bersamaan, 20 guru dan enam admin tambahan. Nilai latensi di bawah dipakai untuk menilai run. Owner dan operator menetapkan target operasional yang akan dipakai untuk rilis. Aturan asesmen mengikuti [PRD dan amendemen aktif](../product/PRD_MAPPING.md).

## Development dan persiapan

1. Checkout bersih pada SHA kandidat. Pakai Node dan pnpm sesuai paket, k6, Playwright Chromium, PostgreSQL 16 dan Redis 7 khusus loopback. Jalankan `pnpm qa validate`, `pnpm qa doctor --profile full`, lalu `pnpm qa run --scenario SIS-001 --profile full`. Gunakan `standard` untuk ADM-001, ADM-002 dan XROLE-001. Jalankan `pnpm test:release-chain` pada checkout bersih yang sama, dengan database localhost `numora_test_job06_<suffix>` dan port 3400–3402 bebas. Simpan hasil per run.
2. Jalankan keyboard/UAT dan verifikasi path yang membutuhkan browser nyata. Fixture lokal membuktikan alur produk dengan data sintetis. Verifikasi Google OAuth, SMTP dan penyimpanan media seperti pada calon deployment di staging. Audit data uji, kontrak dan cakupan tiap manifest sebelum menilai lulus.
3. DevOps menyiapkan staging performa khusus. Rekam SHA web/API/worker, klasifikasi host, VPS/region/tier, jumlah proses, DB pool, rate limit, CDN/cache, fitur aktif, dan jadwal job. Gunakan proyek Auth/database, Redis, bucket media, dan inbox QA yang terisolasi. Rehearsal migrasi dan restore memakai backup yang sesuai. Ukur baseline idle lima menit dan simpan dashboard stage. Jangan menunjuk runner pada cloud Development bersama.
4. Siapkan akun dan content fixtures secara terotorisasi lewat mekanisme provisioning lingkungan. Patokan beban puncak 700 siswa Sekolah dan 300 Mandiri, 20 kelas sekitar 35 siswa, 10 sekolah, 20 guru pemilik kelas, dua admin per subrole. Tetapkan subrole melalui field adminRole pada setiap aktor Admin remote. Tentukan kelas dan siswa yang memang bisa dilihat guru, bab/subbab valid, dan paket aktif dengan ukuran sebenarnya. Untuk burst submit siapkan attempt berisi jawaban dari akun yang sama. Gunakan cohort/paket baru untuk tiap fase satu-kali Pretest dan Tryout. Seed lokal yang membuat konten demo dikhususkan untuk localhost.

## Runner

Jalankan dari root. Salin contoh konfigurasi ke `qa/.local/capacity-config.json`, isi SHA nyata, URL dan parameter yang sesuai, lalu lihat bentuk workload tanpa trafik.

```powershell
node scripts/qa/capacity/run.mjs plan staging load qa/.local/capacity-config.json
node scripts/qa/capacity/run.mjs check staging load qa/.local/capacity-config.json qa/.local/capacity-actors.json
node scripts/qa/capacity/run.mjs run staging load qa/.local/capacity-config.json qa/.local/capacity-actors.json
node --test scripts/qa/capacity/capacity.test.mjs
```

`plan` menampilkan operasi, tahapan dan jumlah akun yang tepat per cohort. `run` menolak URL yang salah, fixture kurang atau token/akun ganda dalam tahap, kontrak operasi yang tidak cocok, serta operasi Produksi di luar izin. Dev mendukung `smoke`, `drill-smoke`, `drill-capacity`, `drill-scale`, `drill-steady`, `load`, `stress`, `pvp`. Staging mendukung `smoke`, `load`, `spike`, `spike-tryout-start`, `spike-tryout-submit`, `spike-drill-submit`, `pvp`, `stress`, `soak`. Prod mendukung `smoke` dan `load`. Set `QA_K6_BIN` bila k6 belum ada di PATH. Pastikan mesin generator sendiri mampu menjalankan workload dengan headroom.

Bentuk bundle aktor adalah `{ "phases": { "<nama tahap>": { "<cohort>": [ { "id": "<UUID profil>", "token": "<token akses>", "affiliation": "school|mandiri", "vars": {} } ] } } }`. Gunakan nama tahap dan jumlah dari `plan`. Isi `chapterId` dan `subchapterId` untuk siswa yang memakai rute tersebut, `classId` untuk siswa Sekolah, `classId`/`studentId` untuk guru, `levelId` untuk Drill, `batchId` dan `schoolId` bila diperlukan untuk Tryout, serta `attemptId` untuk spike submit. Rute yang memakai ID membutuhkan UUID. File aktor dan storage state Playwright tinggal di `qa/.local`. Akun satu cohort berperilaku sebagai satu sesi aktif, dengan jeda acak 8–20 detik pada workload campuran. Sesi remote harus berlaku sampai akhir tiap tahap. Untuk load bertahap, operator boleh mengganti token secara atomik di file aktor sebelum tahap mulai. ID, urutan, role, dan fixture dipertahankan. Untuk soak dua jam, siapkan sesi dari Auth staging yang masa berlakunya mencakup seluruh tahap. Profil awal menyiapkan sesi di luar generator. Refresh sesi nyata dan batas provider diuji sebagai profil operasional terpisah.

Untuk alur asesmen yang menulis, berikan `QA_CAPACITY_EVIDENCE_URL` lewat pengelola rahasia atau shell lokal, dan cocokkan dengan `evidenceDatabaseHost`. Operator staging/prod memasok akses baca terbatas. Snapshot memakai transaksi read-only dan membatasi data ke akun sintetis serta jendela run. End point media, kontrol admin, dan aktivitas tambahan staging bisa disusun pada `extraJourneys` sebagai langkah kontrak, misalnya `{ "operation": "GET /api/v1/admin/reports", "status": 200 }`. Langkah tambahan dijalankan sekali per aktor per tahap, cocok untuk operasi yang bergantung pada fixture atau yang hanya dilakukan sesekali. Body boleh menggunakan token `{classId}` untuk nilai dari `vars`. Gunakan pemeriksaan manual atau suite kanonik untuk rantai yang membuat resource/dokumen lalu menggunakannya, upload multipart, atau penyelesaian melalui operator.

`assets` berisi path nyata `/_next/static/…` dari build yang diuji. Isi `browserSamples` dengan role, device, path, heading yang diharapkan, `readPaths` untuk navigasi/read yang diperlukan, dan path `storageState` di folder ignored. Cadangkan akun sampel browser di luar cohort generator. Browser sample memakai storage state nyata untuk mengukur halaman setelah sesi tersedia. Jalankan smoke login, operasi tulis dan kontrol akses lewat suite browser kanonik dengan akun QA tersendiri. Konfigurasi browser ringan staging membatasi origin dan operasi baca. Smoke browser Prod dijalankan manual sesuai allowlist.

Untuk diagnosis konflik sesi Drill, jalankan `drill-capacity` di Dev. Profil ini hanya menerima penulisan Drill, memakai heartbeat tiap 10 detik, menyebar start dalam delapan detik, dan menjalankan 100 lalu 250 siswa selama lima menit per tahap. Tahap kedua berjalan setelah tahap pertama memenuhi ambang dan rekonsiliasi. Laporan menyertakan kode problem API yang diagregasi per operasi. Gunakan akun terpisah untuk masing-masing tahap agar beban dan hasil mudah ditelusuri. Hasil diagnosis ini memakai jeda baca soal dan dilaporkan terpisah dari benchmark SIS-001 lama.

Untuk menguji kapasitas Drill lokal, jalankan `pnpm qa:capacity run dev drill-scale <config-lokal> <bundle-aktor>`. Siapkan 250, 500, dan 1.000 akun sintetis pada tahap `users-250`, `users-500`, dan `users-1000` di database QA milik run. Masing-masing tahap berdurasi lima menit dengan jeda baca yang sama. Runner memeriksa ambang operasi, minimal 99% akun menyelesaikan Drill per tahap, serta jawaban, hasil, XP, dan outbox di database. Jalankan generator dan layanan QA pada mesin dengan ruang memori yang cukup. Catat keterbatasan lingkungan lokal saat membandingkan hasil dengan Staging.

Profil `drill-steady` menguji 1.000 siswa selama enam menit. Semua akun mulai secara merata selama menit pertama dan tetap dalam fase yang sama setelahnya. Gunakan bundle `users-1000` tersendiri. Ambang dan rekonsiliasi sama dengan `drill-scale`. Laporkan hasil terpisah karena pola kedatangan awalnya berbeda. Selama Drill berlangsung, generator menyimpan jawaban dan mengirim heartbeat. Pembacaan subbab terjadi saat masuk atau memulai percobaan berikutnya, mengikuti navigasi browser.

## Latihan beban campuran lokal

Jalankan `pnpm qa doctor --profile full`, lalu `node scripts/qa/capacity/rehearse.mjs`. Skrip memakai PostgreSQL dan Redis dari konfigurasi uji localhost, membuat database/namespace sendiri, membangun web/API, dan menjalankan listener loopback pada port 3520–3522. Jalankan dari checkout kandidat dan simpan versi di `qa/.local/capacity`. Perintah menghasilkan path laporan dan file `STOP`. Database sementara dan bundel sesi dibersihkan setelah run.

Pool koneksi rehearsal dapat dipilih dengan `QA_CAPACITY_DB_POOL_MAX`, berupa bilangan bulat positif. Default tetap 10. Nilai efektif dicatat sebagai `dbPoolMax` di `candidate.json`. Jalankan seluruh tahapan dengan nilai yang sama dan rekam perbedaan konfigurasi ketika membandingkan run.

Consumer outbox rehearsal memiliki anggaran tersendiri, `QA_CAPACITY_WORKER_DB_POOL_MAX` (default 2), dicatat sebagai `workerDbPoolMax`. Hitung juga koneksi fixture, rekonsiliasi dan administrasi terhadap batas PostgreSQL. Mengubah anggaran rehearsal tidak mengubah konfigurasi Produksi.

Jika generator berbagi mesin dengan database, ukur memori host, API, dan k6 selama fase. `QA_CAPACITY_K6_MEMORY_MIB=1024` memberi Go runtime k6 target memori lunak 1 GiB. Runner menerima opsi ini hanya untuk dev lokal dan mencatatnya di kandidat serta laporan. Pantau CPU generator, jumlah peserta, dan dropped iterations karena target yang terlalu kecil dapat menaikkan biaya garbage collection. [Dokumentasi Go](https://go.dev/doc/gc-guide#Memory_limit).

Untuk mengukur beberapa inti CPU pada satu host, `QA_CAPACITY_HTTP_WORKERS=2` memilih [runtime opsional](../operations/API_CAPACITY_RUNTIME.md) dengan dua worker HTTP dan satu pemilik PvP. Default tetap `0` (satu API). Pool dibagi sebagai anggaran total worker API; `httpWorkers` dicatat pada kandidat. Hasil dengan topologi berbeda dilaporkan terpisah.

**ENGINEERING IMPLEMENTATION — pembacaan PvP.** Proyeksi kolom snapshot dan lock pertandingan disusun sekali dari schema. Nilai tetap berupa parameter SQL, hasil tetap memakai decoder kolom, dan query berjalan dalam transaksi dengan lock serta pemeriksaan peserta yang sama. Tidak ada cache jawaban, hak akses atau status pertandingan. Verifikasi juga timestamp, JSON historis, privasi lawan dan delivery idempoten pada akun runtime non-owner.

**ENGINEERING IMPLEMENTATION — delivery.** Migrasi `0076` menggabungkan query di dalam trigger per butir tanpa mengubah urutan trigger, lock family, validasi pemilik ataupun ledger exposure. Invalidasi reservation dan status cohort tetap atomik dengan exposure yang memicunya. Pembacaan ulang Tryout mengecek manifest immutable bersama query attempt; pencatatan pertama tetap menjalankan fungsi transaksi yang sama. Uji race delivery, rollback pemilik/family palsu, invalidasi pertama, timestamp paparan serta resume saat writer memegang lock. Migrasi hanya dijalankan pada database tes milik run selama rehearsal.

**ENGINEERING IMPLEMENTATION — pembukaan asesmen.** Status Pretest membaca bab, Skip, dan attempt terakhir bersama. Pemilihan paket menyertakan policy yang dipin pada paket tersebut. Daftar batch Tryout hanya membaca membership, attempt dan hasil bila ada batch yang tampil. Pemilihan paket Tryout memakai waktu dari pernyataan SQL yang sama, dan start dengan penilaian parsial mengambil rubrik dalam satu query dengan lock bersama.

Inisialisasi VU k6 memiliki batas 120 detik tersendiri. Waktu workload dimulai saat hook `setup` mengirim tanda siap; PvP dan sampel browser menunggu tanda yang sama. `http.startupMs` mencatat waktu inisialisasi. Durasi fase, ambang latensi dan kelengkapan tetap berlaku. Preflight sesi dan jendela remote mencadangkan 120 detik inisialisasi serta 35 detik penyelesaian per fase; eksekusi remote berhenti saat izin berakhir. Laporan tanpa tanda siap atau ringkasan k6 tidak dianggap lulus.

**ENGINEERING IMPLEMENTATION — autosave.** Saat analytics domain nonaktif, API memvalidasi konten yang dipin lalu menyimpan jawaban dengan satu perintah atomik yang mengunci ulang attempt dan memeriksa pemilik, status, pin, timer/deadline serta waktu database. Perubahan kondisi saat menunggu lock menjalankan ulang jalur validasi terkunci. Saat analytics aktif, jawaban dan event tetap ditulis dalam transaksi yang sama. Tidak ada perubahan rumus nilai, XP atau durasi sesi.

Profil `mixed-local` menjalankan 20 → 100 → 500 → 1.000 siswa dengan 150 detik per tahap. Siswa menjawab dengan jeda 1,2–2,8 detik. Navigasi dan pemantauan memakai jeda 8–20 detik, dan halaman awal asesmen hanya dibaca saat masuk atau memulai percobaan berikutnya. Ia menguji akun sekolah/mandiri, Pretest, Drill, Tryout pilihan ganda demo melalui endpoint paket, PvP, guru dan admin. Gate latensi, kelengkapan submit, dan rekonsiliasi tetap berlaku. Durasi, tipe Tryout, autentikasi sintetis, dan dependensi loopback membatasi perbandingan dengan uji staging yang memakai endpoint batch, OAuth, serta infrastruktur nyata.

## Pemeriksaan sebelum uji staging

Salin `.env.staging.example` ke `.env.staging.local` pada mesin operator dan isi dengan nilai dari inventaris staging. Jalankan `node scripts/check-staging-env.mjs .env.staging.local` sebelum migrasi atau deployment. Pemeriksa membaca berkas lokal dan hanya mencetak nama field bermasalah. URL migrasi dan bukti hanya diberikan ke proses operator yang memerlukannya. Setelah pemeriksaan, gunakan jalur deployment VPS tim untuk web, API, dan worker. Supabase menyediakan Auth dan PostgreSQL.

`check` memeriksa konfigurasi dan fixture secara lokal tanpa mengirim trafik. Ia memvalidasi jendela yang disetujui, pin SHA, bukti smoke/restore yang diwajibkan suite, usia token pada proyeksi tiap tahap, pemisahan paket percobaan sekali jalan, URL bukti PostgreSQL, dan bentuk berkas sesi Playwright. Jika token tahap lanjut perlu diperbarui, periksa ulang dengan bundle baru dan pertahankan ID serta fixture saat rotasi. Status `LOCAL_PREFLIGHT_PASS` hanya membuktikan pemeriksaan berkas.

DevOps mencocokkan SHA kandidat dengan build web/API dan proses worker yang berjalan, proyek Auth/DB dengan inventaris staging, serta endpoint Redis, bucket dan inbox dengan milik staging. Periksa callback OAuth dan login browser, hak SELECT akun bukti, lalu jalankan smoke dengan batch dan akun tersendiri. Catat URL, nama operator, jendela WIB, referensi restore dan run smoke, serta metrik idle lima menit. Set `pvp: true` untuk uji campuran yang mewajibkan PvP. Uji koneksi dan satu pertandingan sebelum menjalankan load. Bila dependensi atau bukti gagal, tandai uji staging BLOCKED dan gunakan jadwal tersebut untuk latihan lokal.

## Izin Prod, penghentian dan laporan

1. DevOps mengisi `authorization` dari approval yang telah direkam. Samakan SHA dengan referensi CI hijau dan staging yang lulus. Isi operator, referensi jadwal, batas siswa, jendela waktu, suite, dan operasi yang diizinkan. Burst khusus menambah 100 siswa pembaca sebagai beban latar, jadi profil tersebut perlu cap 1.100 akun siswa QA. Runner mengizinkan operasi baca yang tercantum pada katalog. Untuk submit/tulis asesmen, tambahkan bukti bahwa efek akun QA telah benar-benar dipisahkan dari leaderboard, IRT, analytics, notifikasi dan konten publik. Verifikasi lewat smoke yang sah dan readback sebelum mengaktifkan operasi. Jika pemisahan belum tersedia, gunakan profil baca di Prod. Jalankan semua alur berisiko termasuk publikasi dan rilis IRT di staging. Penilaian kapasitas Prod mengikuti cakupan izin yang benar-benar dijalankan.
2. Operator meninjau ambang awal. Perjalanan inti ≥99% berhasil, gabungan 5xx/timeout/429 tak terduga <1% per operasi yang memiliki ≥100 sampel. Runner juga mencatat peserta yang berhasil start/submit pada tahap yang cukup panjang. Target p95 baca ≤750 ms, simpan ≤1 detik, submit ≤2 detik dan acknowledgment PvP ≤1 detik. Simpan p99; untuk volume sampel kecil, telusuri setiap kegagalan. Bukti integritas mensyaratkan nol jawaban terakui hilang, nol finalisasi/XP ganda, dan nol kebocoran akses. Cocokkan acknowledgment dengan attempt, jawaban, XP, dan event outbox; pisahkan commit tanpa acknowledgment untuk investigasi.
3. DevOps menghentikan trafik pada dampak pengguna, kesalahan integritas, kebocoran akses, OOM/restart, pool habis, generator jenuh, 2% error selama dua menit, atau dua health probe gagal. Buat file `STOP` pada path yang dicetak runner atau kirim Ctrl+C. Runner memeriksa health sebelum mengirim beban tiap tahap dan ikut menghentikan saat dua health probe gagal, integritas rusak, atau batas error keamanan k6 terlampaui. Alarm operator memakai jendela rolling dua menit; trip k6 memakai rate kumulatif sejak tahap mulai. Setelah penghentian, ukur 10 menit pemulihan human-observed: latency/error, CPU/RAM, DB pool, backlog dan dampak akun. Gunakan [instrumentasi yang sudah ada](../development/DATABASE_RUNTIME_METRICS_2026-11-14.md).
4. `report.json` dan k6 summary di `qa/.local/capacity/<run>` menyimpan ukuran tahap, hasil transport/persistensi, operasi, throughput, p95/p99 dan alasan stop. Lampirkan grafik metrik runtime, trafik nyata dan QA, hasil Google OAuth/browser, operasi allowlist, dan tabel PASS/FAIL/BLOCKED/NOT RUN. Catat waktu WIB, versi, sumber fixture dan selisih konfigurasi. QA menilai batas klaim, DevOps menjaga jendela dan stop, developer menangani defect. Ulangi bukti yang terdampak dan kapasitas kandidat pada SHA baru. Bersihkan resource sintetis milik run saja sesuai prosedur lingkungan.
